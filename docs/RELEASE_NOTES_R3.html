BM25
Sparse · keyword
rank-bm25 (BM25Okapi) in-process. BM25Corpus built from ChunkModel list — reusable across queries. No embedder needed. Beats dense on exact keywords, rare terms, acronyms, product codes.
k1 (TF saturation) b (length norm) top_n_factor
Hybrid (RRF)
Dense + Sparse fusion
Reciprocal Rank Fusion of Dense + BM25. Rank-based — sidesteps score-scale mismatch. Deduplicates by chunk_id. rrf_score in metadata. Alpha controls blend.
alpha rrf_k dense_top_k bm25_top_k
MMR
Diversity-aware
Maximum Marginal Relevance (Carbonell & Goldstein, 1998). Greedy selection: λ × relevance − (1−λ) × max_sim_to_selected. Kills near-duplicate chunks in top-k.
lambda_mult fetch_k
Re-Ranker
Cross-encoder · composable
Stage 1: dense fetch_k candidates. Stage 2: CrossEncoder re-ranks jointly. Lazy model load. Composable — any retriever feeds Stage 1. score_threshold post-filter.
model_name fetch_k batch_size score_threshold
Compression
Contextual filter · composable
Stage 1: dense fetch_k candidates. Stage 2: keyword (token overlap) or LLM-based passage extraction. Composable — any retriever feeds Stage 1.
strategy (keyword|llm) min_keyword_overlap fetch_k
Algorithm
Reciprocal Rank Fusion
The most interview-relevant algorithm in this release. RRF fuses on ranks — not scores — which sidesteps the dense-vs-sparse scale mismatch entirely.
RRF Score
RRF(d) = α × 1 / (k + rank_dense(d)) + (1−α) × 1 / (k + rank_bm25(d))
k = 60 (default) — flattens score distribution, reduces sensitivity to rank-1 outliers.
α — dense weight. 1.0 = pure dense. 0.0 = pure BM25. 0.5 = balanced.
Rank-based — 1st place always contributes 1/(k+1) regardless of raw score. No normalisation needed across incompatible score spaces.
QuestionAnswer
Why RRF over score interpolation?Dense scores and BM25 scores live on different scales. Normalising is fragile. Ranks are always comparable integers.
Why k=60?Empirically optimal in TREC experiments. Higher k = flatter distribution = less sensitivity to top-rank dominance.
What does alpha=1.0 give you?Pure dense retrieval. BM25 contributes 0. Useful for baseline comparison in the Comparison UI.
When does BM25 win?Exact keywords, rare terms, codes, product names — where embeddings blur lexical specificity.

Interview Angles
What R3 Unlocks
"How does hybrid retrieval combine sparse and dense?"
RRF on ranks, not raw scores — avoids normalising incompatible score scales. α × 1/(k + dense_rank) + (1−α) × 1/(k + bm25_rank). Most candidates hand-wave score-weighting and get the scale problem wrong.
"When does BM25 beat dense?"
Exact keywords, rare terms, codes, product names, acronyms — where embeddings blur lexical specificity. Hybrid exists because neither wins alone across all query types.
"What's MMR for?"
Kills near-duplicate chunks in the top-k. Trades a little relevance for diversity via lambda_mult. Critical when your corpus has repetitive passages (policy docs, legal boilerplate).
"Re-ranking cost/benefit?"
Cross-encoders are accurate but expensive. Over-fetch cheaply with a bi-encoder (dense, fast), then re-rank a small candidate set with the cross-encoder. The fetch_k → top_k funnel is the pattern.
"Composable retrievers?"
Re-ranker and Compression wrap any base retriever — Dense, BM25, or Hybrid for Stage 1. Strategy + decorator pattern applied to retrieval. Swapping the base is a config change, not a code change.
"CI/CD without static credentials?"
OIDC federated identity for both Azure and AWS. GitHub Actions requests a short-lived token at runtime; no AWS_ACCESS_KEY_ID or AZURE_CLIENT_SECRET stored in repo secrets. Secrets in Key Vault / Secrets Manager, not env vars.
